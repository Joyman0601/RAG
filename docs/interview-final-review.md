# 企业知识库 RAG + Agent 助手项目复盘

## 项目一句话介绍

这是一个基于 Spring Boot 的企业知识库 RAG + Agent 助手项目：把企业文档异步入库、向量检索、LLM 问答、工具调用、安全权限和生产治理串成一套可演示、可扩展、可面试讲清楚的大模型应用后端。

## 一、LLM 接入层

### 实现了什么

- 封装统一的 `LlmClient`，负责调用大模型生成接口。
- 封装 `EmbeddingClient`，负责把文本转成向量。
- 支持模型配置、API Key、Base URL、超时、代理等参数化配置。
- 对 LLM 调用异常做分类，例如配置缺失、API Key 缺失、HTTP 错误、超时、空响应、结构化输出异常等。
- 在生成结果中保留 token usage，用于后续成本统计和限额控制。
- 为 Embedding 增加本地缓存，避免重复文本反复调用 embedding 接口。

### 为什么这样设计

LLM 和 Embedding 是外部依赖，不能把调用细节散落在业务代码里。统一封装之后，业务层只关心“生成回答”和“生成向量”，不关心 HTTP、鉴权、超时、异常解析等细节。

另外，LLM 调用成本高、失败模式复杂，所以这里没有简单抛一个通用异常，而是把错误类型结构化，方便上层做重试、降级、提示和指标统计。

### 面试可讲亮点

- LLM 接入层不是直接在 Controller 里调接口，而是抽象成独立客户端，降低业务耦合。
- Embedding 单独封装，因为它和 Chat Completion 的接口、模型、超时、失败处理都不同。
- LLM 返回 token usage 后，项目可以做成本治理，而不是只做一个 Demo 级问答。
- Embedding 缓存按模型和文本 hash 生成 key，避免泄露原始文本，也避免模型切换导致缓存污染。

### 常见追问回答

**问：为什么要区分 LLM Client 和 Embedding Client？**

答：两类调用虽然都属于大模型能力，但用途和约束不同。Chat 是生成式接口，关注上下文、输出 token、结构化响应；Embedding 是向量化接口，关注输入文本、向量维度和批量处理。分开封装以后，超时、缓存、错误处理和后续替换模型都会更清晰。

**问：如果 LLM 接口不稳定怎么办？**

答：当前项目已经做了错误分类和超时控制，上层可以根据错误类型决定是否重试。比如文档入库时 embedding 失败属于可重试场景，可以交给异步任务重试；用户在线问答更适合快速失败并返回友好提示。后续可以接入 Resilience4j 做熔断、限流和重试策略。

**问：为什么 Embedding 缓存不直接用原文做 key？**

答：直接用原文会有隐私和 key 过长的问题。项目里使用文本 hash，再拼上 embedding 模型，既能避免泄露内容，也能避免不同模型生成的向量混用。

## 二、RAG 知识库层

### 实现了什么

- 实现文档、切片、向量检索和问答链路。
- 文档包含 `status`、`visibility`、租户、部门、角色、版本等字段。
- 检索时支持 topK、scoreThreshold、是否包含低分结果等参数。
- RAG 问答返回 answer 的同时返回可信 sources，包括 documentId、filename、chunkId、score 和内容预览。
- 增加知识库版本号，用于检索缓存失效。
- 增加 RAG search cache，按租户、权限签名、问题 hash、topK、阈值、embedding 模型、知识库版本生成缓存 key。
- 增加 RAG Eval 相关模型和服务，用于批量评测回答质量。

### 为什么这样设计

RAG 的核心不是“把文档塞进 prompt”，而是要保证检索结果可信、可追溯、权限正确、版本一致。企业场景里，文档不是静态文本，可能会更新、删除、重新入库，所以用文档版本和状态控制检索范围。

同时，RAG 检索的成本主要在 embedding 和向量搜索。对相同用户权限、相同知识库版本、相同问题的检索结果做短 TTL 缓存，可以降低重复请求成本。

### 面试可讲亮点

- RAG 回答带 sources，避免黑盒回答，方便用户验证来源。
- 文档使用 version/status 管理生命周期，避免旧版本切片被检索出来。
- 检索缓存 key 包含权限签名和知识库版本，解决“缓存命中但权限或文档已变化”的问题。
- 向量检索不是只按相似度，还把租户、部门、角色、文档状态等过滤条件下推到检索请求。
- RAG Eval 支持把问答质量从人工感觉变成可批量评估。

### 常见追问回答

**问：RAG 为什么要返回 sources？**

答：企业知识库场景很重视可信度。只返回答案，用户不知道模型依据是什么，也无法判断是否幻觉。返回 sources 后，前端可以展示引用文档和片段，用户能回查来源，也方便调试召回质量。

**问：为什么要有文档 status？**

答：文档从上传到可检索不是瞬间完成的，中间会经历切片、embedding、写入向量库等步骤。`PENDING`、`PROCESSING`、`READY`、`FAILED` 等状态可以避免未完成或失败文档进入检索结果。

**问：为什么缓存 key 要包含权限签名？**

答：同一个问题，不同用户能看的文档不同。如果缓存 key 只按问题生成，A 用户的检索结果可能被 B 用户命中，造成越权泄露。权限签名把租户、用户、部门、角色等信息纳入 key，可以避免这个问题。

## 三、文档异步入库层

### 实现了什么

- 上传文档后不直接同步完成入库，而是创建 `DocumentIngestTask`。
- `IngestWorker` 定时扫描可执行任务，处理文档解析、切片、embedding、向量写入等步骤。
- 任务有状态机：`PENDING`、`RUNNING`、`RETRYING`、`SUCCESS`、`FAILED`、`CANCELED`。
- 任务记录当前步骤、重试次数、最大重试次数、错误码、错误信息、锁定 worker 和锁定时间。
- 支持失败重试、指数退避、运行超时恢复。
- 支持文档版本校验，如果旧版本任务完成时发现不是当前版本，会取消任务，避免覆盖新版本数据。

### 为什么这样设计

文档入库是重任务，可能涉及大文件解析、文本切分、多个 embedding 调用和向量存储写入。如果上传接口同步等待，用户体验差，也容易因为 LLM 或网络超时导致请求失败。

异步任务模型可以把“用户上传”和“后台处理”解耦。任务状态可查询，失败可重试，worker 崩溃后也能通过锁超时恢复。

### 面试可讲亮点

- 文档入库设计成任务状态机，而不是一次性同步方法。
- 通过 documentVersion 保证幂等和版本一致性。
- 任务带 currentStep 和错误码，方便排查是解析失败、embedding 失败还是写向量失败。
- 对网络和 LLM 临时错误做可重试，对业务错误做不可重试。
- worker 使用锁定字段和超时恢复，具备从单机内存版扩展到数据库/MQ 任务表的空间。

### 常见追问回答

**问：为什么不直接在上传接口里完成入库？**

答：入库链路耗时不可控，尤其 embedding 调用依赖外部服务，同步接口会导致超时和用户等待。异步任务可以快速返回上传结果，再由后台处理，用户可以通过状态查询处理进度。

**问：怎么保证重复上传或重复执行不出错？**

答：项目通过 documentVersion 和任务状态控制幂等。每次文档更新产生新版本，worker 处理时会校验当前任务版本是否仍然是最新版本。如果不是最新版本，就取消旧任务，避免旧切片覆盖新文档。

**问：如果 worker 执行中宕机怎么办？**

答：任务有 lockedAt 和锁超时时间。扫描任务时会恢复超时的 RUNNING 任务，把它转成 RETRYING，这样后续 worker 可以继续处理。当前是内存实现，生产环境可以迁移到数据库或 MQ。

## 四、Tool/Agent 层

### 实现了什么

- 实现工具注册、工具定义、工具参数校验、工具执行和结果封装。
- Agent Chat 支持一次模型决策、一次工具调用、再生成最终回答。
- Agent Loop 支持多步循环，限制最大步骤数、最大 LLM 调用次数和最大执行时长。
- 工具执行前做后端裁决：工具是否存在、用户是否有权限、参数是否合法、高风险工具是否确认、灰度策略是否允许。
- 支持 `search_knowledge_base` 工具，让 Agent 可以调用 RAG 检索企业知识库。
- 支持高风险工具确认机制，比如取消订单类工具不能直接自动执行。
- 支持 Shadow Mode：模型可以“选择”工具，但后端只记录决策，不实际执行。
- 记录 Agent step、tool debug info、shadow decision，便于调试和审计。

### 为什么这样设计

Tool Calling 不能完全相信模型。模型只能提出工具调用意图，真正是否执行必须由后端裁决。企业场景里，工具可能涉及订单、退款、权限数据和内部知识库，如果只靠 prompt 约束模型，很容易出现越权、误执行或参数注入。

所以项目把 Agent 分成“模型决策”和“后端执行”两个阶段：模型负责理解用户意图，后端负责权限、风控、参数校验和执行。

### 面试可讲亮点

- Tool Calling 采用后端裁决模型，不让 LLM 直接执行工具。
- 工具参数使用 JSON 反序列化和 Bean Validation 校验，并禁止 userId、tenantId、role 等敏感参数由模型传入。
- 高风险工具需要确认，防止模型误操作。
- Agent Loop 有最大步骤、最大模型调用和超时限制，避免无限循环和成本失控。
- Shadow Mode 可用于灰度上线：先观察模型是否会选对工具，再决定是否真实执行。

### 常见追问回答

**问：为什么不能让模型直接调用工具？**

答：模型输出不可信，可能传错参数、绕过权限，甚至被用户 prompt injection 诱导。后端必须把模型输出当成“建议”，再做工具白名单、权限、参数、风险等级、灰度策略等校验，最终由后端决定是否执行。

**问：Agent Loop 怎么避免死循环？**

答：项目里设置了最大步骤数、最大 LLM 调用次数、最大执行时长，并记录重复工具调用。达到限制后会停止并返回明确错误码，同时记录指标。

**问：Shadow Mode 有什么价值？**

答：新工具上线时，不一定马上让模型真实执行。Shadow Mode 可以只记录模型是否选择了该工具、参数是什么、是否通过校验、被什么策略拦截。这样可以先观察准确率和风险，再逐步放量。

## 五、安全权限层

### 实现了什么

- 定义当前用户上下文，包括 userId、tenantId、部门、部门集合、角色集合、权限集合等。
- 工具执行时根据 permissionCode 校验用户是否有权限。
- RAG 检索时把租户、用户、部门、角色、文档可见性、文档状态下推到向量检索请求。
- 工具参数校验时禁止模型传入 userId、tenantId、roleId、departmentIds、visibility 等敏感字段。
- 高风险工具必须走确认流程。
- 全局异常处理把内部错误映射成结构化错误响应。

### 为什么这样设计

企业知识库和企业工具调用都属于权限敏感场景。不能只在接口入口做权限，因为 Agent 工具参数由模型生成，模型可能被诱导传入别人的 userId 或 tenantId。因此，真实身份必须来自后端上下文，而不是模型参数。

RAG 权限也不能只在回答生成后过滤，因为一旦越权文档进入 prompt，就已经泄露给模型了。更合理的方式是检索阶段就过滤。

### 面试可讲亮点

- 用户身份由后端注入 ToolExecutionContext，不允许模型伪造。
- 权限过滤下推到检索层，避免越权内容进入 prompt。
- 工具参数有敏感字段黑名单，防止 prompt injection 诱导模型构造越权参数。
- 高风险操作和普通查询工具区分风险等级。
- 错误码结构化，方便前端展示和审计。

### 常见追问回答

**问：RAG 权限为什么要在检索阶段过滤？**

答：如果先检索再过滤，越权内容可能已经进入 prompt，被模型看到并参与生成，这本身就是泄露。权限过滤下推到检索请求，能保证模型只接触当前用户有权访问的切片。

**问：模型传 userId 怎么办？**

答：项目里对工具参数做了敏感字段拦截，`userId`、`tenantId`、`roleIds`、`departmentIds` 等字段不允许出现在模型生成的工具参数里。真实用户身份只从后端上下文取。

**问：当前权限实现是否生产可用？**

答：当前是 mock current user，适合演示核心链路。生产环境会对接真实登录态，例如 Spring Security + JWT，把租户、角色、部门、权限从认证中心或用户服务中加载。

## 六、生产治理层

### 实现了什么

- 成本治理：token 估算、调用前预算检查、租户/用户额度、接口限流、用量记录。
- 指标统计：API 请求数、错误数、LLM 调用数、LLM 错误数、token 总量、RAG 无答案次数、Agent 达到最大步骤次数、工具失败次数。
- 请求追踪：为每个请求生成或透传 `X-Request-Id`，写入 MDC，日志中记录 requestId、tenantId、userId、latency、status、errorCode。
- 告警规则：根据 LLM 错误率、RAG 无答案率、Agent 最大步骤次数、token 使用量触发日志告警。
- 灰度策略：按工具 enabled、tenant、role、shadowOnly、autoExecute、requiresConfirmation、maxCallsPerRequest 等配置裁决工具可用性。

### 为什么这样设计

大模型应用上线后的核心问题不是“能不能回答”，而是成本、稳定性、可追踪性和风险控制。LLM 调用会产生费用，Agent 可能循环调用，工具可能失败，RAG 可能召回不到答案，所以必须有指标和治理能力。

项目里虽然是内存实现，但结构上已经把生产治理点拆出来，后续替换 Redis、Prometheus、配置中心会比较自然。

### 面试可讲亮点

- 成本治理前置到 LLM 调用前，而不是调用后才统计。
- 记录 token usage 和接口维度用量，方便做租户计费或限额。
- 请求链路有 requestId，方便排查一次用户请求经历了哪些 LLM、RAG、Tool 调用。
- Agent 最大步骤和 LLM 最大调用数都受成本治理约束。
- 工具灰度不是写死在代码里，而是抽象成策略对象，便于后续接配置中心。

### 常见追问回答

**问：为什么要在调用前做 token 预算检查？**

答：如果输入上下文过长，LLM 可能报错或产生高成本。调用前估算 token，可以提前截断或拒绝，避免无效调用和成本失控。

**问：当前指标为什么不用 Prometheus？**

答：当前项目重点是展示治理思路，先用内存指标和日志告警实现闭环。生产环境会把 `MetricsService` 替换或适配到 Micrometer + Prometheus + Grafana。

**问：灰度策略在 Agent 里有什么作用？**

答：新工具上线不应该立刻全量开放。灰度策略可以按租户、角色、是否 shadowOnly、是否需要确认、最大调用次数来控制工具可见性和执行权，降低误调用风险。

## 高频面试问题与参考答案

### 1. 这个项目和普通 ChatGPT 套壳有什么区别？

普通套壳主要是把用户问题转发给模型。本项目重点在企业应用后端：有文档入库、向量检索、可信 sources、权限过滤、Agent 工具调用、后端裁决、成本治理、指标和灰度。它解决的是企业知识库和业务工具安全接入问题，不只是聊天 UI。

### 2. RAG 的完整链路是什么？

文档上传后创建入库任务，后台 worker 解析文档、切片、调用 embedding、写入向量存储。用户提问时，系统对问题做 embedding，按权限和文档状态检索相关切片，构造上下文 prompt 调用 LLM，最后返回答案和 sources。

### 3. 如何降低 RAG 幻觉？

第一，系统 prompt 明确要求只基于资料回答；第二，检索不到结果时返回固定无答案文案；第三，回答带 sources，用户可以追溯；第四，通过 scoreThreshold 控制低相关片段；第五，后续可以加入 rerank、引用约束和答案一致性评估。

### 4. 如何保证用户只能看到有权限的知识？

权限在检索阶段下推。检索请求包含 tenantId、userId、departmentIds、roleIds、文档 status 和 visibility 等字段，向量检索只返回当前用户可访问的切片。同时缓存 key 包含权限签名，避免不同权限用户复用同一缓存结果。

### 5. 文档更新后，旧向量怎么办？

项目里文档有 version 和 status。新版本入库时，任务携带 documentVersion；worker 写入时校验版本，旧任务会被取消。检索请求也会带 ready document version 快照，避免旧版本切片进入结果。生产环境可以进一步在向量库中按 documentId + version 删除旧向量。

### 6. Tool Calling 为什么要后端裁决？

LLM 输出不能直接信任。用户可能通过 prompt injection 诱导模型调用高风险工具，或伪造 tenantId、userId。后端裁决可以统一做工具白名单、权限、参数校验、风险等级、确认流程和灰度策略，保证最终执行权在后端。

### 7. Agent 如何控制成本？

项目里有 token 估算、调用前预算检查、租户/用户额度、接口限流、最大 Agent 步骤、最大 LLM 调用次数和执行超时。每次 LLM 调用后记录 token usage 和成本估算，用于后续统计和限制。

### 8. 异步入库为什么需要状态机？

文档入库步骤多、耗时长、容易失败。状态机能清晰表达任务处于等待、运行、重试、成功、失败还是取消状态。配合 currentStep、错误码和重试次数，可以做进度查询、故障排查和失败恢复。

### 9. Shadow Mode 是什么，解决什么问题？

Shadow Mode 是工具灰度的一种方式：模型可以选择工具，系统记录这次工具决策、参数、校验结果和拦截原因，但不真实执行。它适合新工具上线前观察模型选择是否准确，降低误执行风险。

### 10. 这个项目如何从 Demo 演进到生产？

主要替换基础设施：向量存储换成 Milvus、pgvector 或 Elasticsearch 向量检索；用户身份换成 Spring Security + JWT；异步任务换成 MQ；缓存和限流换成 Redis；指标接入 Micrometer + Prometheus；灰度策略接入 Nacos、Apollo 或其他配置中心。

## 项目亮点专项整理

### 可信 sources

回答不仅返回自然语言，还返回引用来源，包括 documentId、filename、chunkId、score 和内容预览。这样用户能知道答案依据，面试时可以强调这是企业知识库区别于普通聊天机器人的关键点。

### 文档 version/status

文档不是简单文本，而是有生命周期和版本。`status` 控制文档是否可检索，`version` 控制文档更新后的切片一致性。这样可以避免未完成文档、失败文档、旧版本文档被召回。

### 异步入库幂等

入库任务携带 documentVersion，worker 处理时校验当前版本。如果任务过期，就取消而不是继续写入。失败任务根据错误类型决定是否重试，并有锁超时恢复机制。这体现了后端工程能力。

### Tool Calling 后端裁决

模型只负责提出工具调用意图，后端负责最终执行判断。工具调用必须经过工具存在性校验、参数校验、权限校验、风险确认、灰度策略和调用次数限制。这是 Agent 落地的安全边界。

### 权限过滤下推

RAG 检索请求携带租户、用户、部门、角色、文档状态等条件，在检索阶段就过滤，避免越权切片进入 prompt。这个点适合回答企业级 RAG 和个人知识库 RAG 的区别。

### Shadow Mode

Shadow Mode 用于新工具灰度：记录模型选择工具的情况，但不真实执行。它能帮助团队在上线前评估工具选择准确率、参数质量和潜在风险。

## 项目不足和后续优化方向

### 真实向量库

当前向量存储偏演示和内存实现，适合讲清楚检索流程。生产环境应替换为 Milvus、pgvector、Elasticsearch、OpenSearch 或云厂商向量库，支持持久化、索引、过滤下推和水平扩展。

### 真实登录权限

当前用户上下文是 mock 实现。后续应接入 Spring Security + JWT/OAuth2，从认证中心解析租户、用户、角色、部门和权限，并结合企业组织架构服务动态刷新权限。

### MQ

当前文档入库 worker 基于定时扫描。生产环境可以引入 RabbitMQ、Kafka、RocketMQ 或云消息队列，把文档入库任务事件化，提升吞吐、削峰和失败重试能力。

### Redis

当前缓存、限流、额度统计是内存版。生产环境应使用 Redis 存储 RAG search cache、embedding cache、rate limit counter、quota usage 和分布式锁，支持多实例部署。

### Prometheus

当前指标是内存计数和日志告警。后续可接入 Micrometer + Prometheus + Grafana，把 LLM 调用量、错误率、token 成本、RAG 无答案率、工具失败率可视化。

### 灰度配置中心

当前灰度策略可以配置化，但仍偏本地配置。生产环境可以接入 Nacos、Apollo 或 Spring Cloud Config，实现工具开关、租户白名单、角色白名单、shadowOnly、自动执行等策略动态调整。

## 2 分钟项目介绍稿

我这个项目是一个基于 Spring Boot 的企业知识库 RAG + Agent 助手后端，目标不是简单套一个大模型接口，而是模拟企业里真正落地大模型应用会遇到的问题：文档怎么入库、知识怎么检索、回答怎么可信、权限怎么控制、Agent 工具怎么安全执行，以及上线后成本和稳定性怎么治理。

整体链路分成几层。第一层是 LLM 接入层，我封装了 Chat 和 Embedding 两类客户端，统一处理模型配置、超时、异常分类和 token usage。第二层是 RAG 知识库层，文档上传后会被切片、向量化、写入向量存储；用户提问时会按 topK 和相似度阈值召回切片，并返回答案和可信 sources。这里我特别加了文档 version/status，避免未完成或旧版本文档被检索出来。

第三层是文档异步入库。因为解析、切片、embedding 都是耗时操作，所以我没有在上传接口同步处理，而是设计了入库任务和 worker。任务有状态、步骤、重试次数、错误码和锁超时恢复，并通过 documentVersion 保证幂等。

第四层是 Agent 和 Tool Calling。模型不会直接执行工具，只能提出工具调用意图，后端会做工具白名单、参数校验、权限校验、高风险确认、灰度策略和调用次数限制。这个设计能防止模型被 prompt injection 诱导越权或误操作。同时我还实现了 Shadow Mode，新工具可以先只记录模型决策，不真实执行，用于灰度观察。

最后是生产治理层，包括 token 预算、限流、额度、用量记录、请求 traceId、指标统计和告警规则。虽然目前很多基础设施是内存实现，但边界已经拆清楚了，后续可以把向量库换成 Milvus 或 pgvector，把缓存和限流换成 Redis，把异步任务换成 MQ，把指标接入 Prometheus，把灰度策略接入配置中心。

所以这个项目我想体现的是 Java 后端转大模型应用开发时的核心能力：不仅会调模型接口，还能把 RAG、Agent、安全权限、异步任务和生产治理结合起来，做成一个可维护、可扩展的企业级后端架构。
